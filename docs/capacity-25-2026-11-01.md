# 25-student capacity validation — November 1, 2026

The optimized application passed an isolated 25-student mixed-use simulation with default Sheets quotas enforced. This supports a target of 25 students for the tested workload; it is not a measured production maximum or an availability guarantee.

The fixture ended with 300 review logs, 250 distinct progress rows, and 53 study sets: 25 initial sets, 25 manual saves, and three generated sets. Every successful rating had a persisted review log. The two-worker queue also passed a separate probe: six submissions accepted, two running and four waiting, the seventh rejected, duplicate-account submission rejected, and all six completed after releasing the simulated provider.

The [earlier baseline](performance-2026-11-01.md) hit quota-induced 16.6-second card-rating p95 at just two fast reviewers. The optimized test sustained 25 students with about two-second rating latency, primarily the intentional batch collection window. The public browsing baseline separately passed 40 paced virtual sessions without errors; it did not measure a maximum.

## What changed

`CardProgress` and `ReviewLogs` now load together through one Sheets batch read and share a committed-data cache, refreshed after 60 seconds when safe. Progress refreshes immediately after a successful rating need no additional review-history reads. Study-set snapshots refresh every 30 seconds, and successful saves/updates update loaded snapshots instead of discarding them.

Concurrent ratings collect for up to two seconds and write their progress and logs together in one atomic values batch. Requests wait for the durable write before returning success. Retries repeat identical fixed row ranges, which prevents an uncertain HTTP reply from appending duplicate rows. Separate locks serialize calculations for the same card; different students can share a batch. Deletion drains pending ratings and invalidates row mappings, cached sets, and grid dimensions, including when a deletion's HTTP reply is lost. Grid capacity grows in chunks before fixed-row writes reach the boundary.

The dependency-free audit verifies that the first isolated card interaction costs one batch read and one batch write, an immediate progress refresh costs zero extra calls, and the next warm interaction costs zero review reads plus a write. Multiple students share that write in the concurrent test. Authentication, schema and study-set I/O are additional; the complete 25-student simulation includes account/profile lookups and normal set operations.

## Test scope and assumptions

The harness ran the real FastAPI routes, signed-session verification, account/profile checks, storage serialization, caches, review scheduling, generation fallback/batching, queue and Sheets retry logic. All accounts were synthetic. A thread-safe memory adapter replaced Sheets HTTP, with an assumed 50 ms latency per attempt and separate rolling 60-second budgets of 60 reads and 60 writes. Google's [published quotas](https://developers.google.com/workspace/sheets/api/limits) apply per service identity; actual project quotas and refill timing may differ.

Each student loaded their library, progress and due cards, saved one small set, then rated a card and refreshed progress every ten seconds. Three students also generated ten questions, using two simulated five-second provider responses each. Initial schema headers already existed. The test ran on the local Windows machine through ASGI TestClient, so it does not measure Render CPU/RAM, Google transport latency, actual model-provider latency/quotas, OCR, large uploads or historical datasets, browser rendering, social chat traffic, or a full class generating simultaneously.

The background generator still runs two jobs concurrently and admits six running/queued jobs. Twenty-five students can study while a few generate; this change does not provide 25 simultaneous AI generations. Provider quotas remain independent of Sheets.

Run one API process and one writer per spreadsheet. Independent replicas/workers or concurrent manual edits to the review tables are unsupported because row reservations and room state live in the API process. Successfully acknowledged ratings are on Sheets, so the cache can rebuild after a restart. An unacknowledged request interrupted by a restart must be retried by the client.

## Reproduce

Use a backend Python environment plus `httpx`, or the temporary-dependency setup documented in the script:

```powershell
python scripts/stress-test-mixed.py --capacity-25 --output docs/capacity-25-repeat.json
python scripts/audit-study-capacity.py
python -m unittest discover -s backend -p 'test_*.py' -q
node --test tests/*.test.mjs
```

Raw data: [capacity-25-2026-11-01.json](capacity-25-2026-11-01.json). The harness cannot target a live URL and blocks external traffic. Existing baseline measurements remain preserved in their original JSON files.
